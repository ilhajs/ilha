ilha is built around a small set of ideas: islands, signals, JSX rendering, and function-component primitives. Once these click, the rest of the library feels straightforward.

## Islands

An island is a function component that can render itself to HTML on the server and mount itself in the browser. It owns its own state, behavior, and rendering, so each piece of interactivity stays local and explicit.

This makes ilha a good fit for server-rendered pages that only need interactivity in specific places. Instead of turning the whole page into one client app, you can activate only the parts that need to be interactive.

A plain JSX function is not an island boundary. It is a transparent component whose events and reactive reads belong to the containing island. Wrap it with `ilha()` only when it needs independent ownership.

## Choose the smallest component form

Start with the least machinery your component needs:

| Form                           | Ownership                                                           |
| ------------------------------ | ------------------------------------------------------------------- |
| `const View = () => JSX`       | The containing island owns its rendering, events, and cleanup       |
| `const View = ilha(() => JSX)` | `View` owns an independent reactive scope, lifecycle, and hydration |

Promotion keeps the markup intact. A component without props can wrap the same render function directly. For a component with props, pass them straight to the component:

```tsx twoslash
import { ilha } from "ilha";

const BadgeView = ({ label }: { label: string }) => (
  <span>{label}</span>
);

const Label = ilha<{ label: string }>(({ label }) => (
  <BadgeView label={label} />
));
```

## Isomorphic components

The same island can be used in two ways:

- Rendered to an HTML string for SSR.
- Mounted into a DOM element for client-side interactivity.

That means you do not have to split a component into separate "server" and "client" versions. One definition can handle both output and activation.

## Signals

ilha uses signals for reactive state. A signal is a value you can read and update; when it changes, the island reacts.

A state accessor works as both a getter and setter:

```ts twoslash
import { signal } from "ilha";

const count = signal(0);
count(); // read
count(5); // write
```

Inside JSX, render the signal value directly:

```tsx twoslash
import { signal } from "ilha";

const count = signal(0);
<p>{count()}</p>;
```

## Function-component primitives

For an island, declare reactive capabilities as primitives inside the component, in a stable order:

```tsx twoslash
import { ilha, state, derived, action } from "ilha";

const Counter = ilha(() => {
  const count = state(0); // local reactive state
  const double = derived(() => count() * 2); // derived computed value
  const increment = action(() => count((v) => v + 1)); // reusable operation

  return <button onclick={increment}>{double()}</button>;
});
```

Primitives persist across rerenders by call order — the component reruns in place when a reactive value it reads changes. In development, ilha warns about primitive calls outside an island render, hook count changes, and kind changes at a slot.

## JSX rendering

ilha renders islands with JSX. Configure TypeScript with `jsxImportSource: "ilha"`, then return JSX from the component:

```tsx twoslash
import { ilha } from "ilha";

const userInput = "edited by the user";
const Message = ilha(() => <p>{userInput}</p>);
```

JSX output follows safe rendering rules: interpolated values are escaped by default, arrays render without commas, and child islands can be nested directly. If you need to inject trusted markup, opt into that explicitly with [`raw()`](/guide/helpers/raw).

## Derived values

Not every value belongs in local state. Sometimes a component needs data that depends on state or props, including async data.

That is what [`derived()`](/guide/island/derived) is for. Read it with the same call syntax as state. For async work, the accessor also exposes `loading`, `value`, and `error`, so loading and error states stay part of the normal rendering model.

## Events and effects

ilha separates user interaction from side effects.

Use [native handlers and `action()`](/guide/island/action) for DOM events and reusable operations. Use [`effect()`](/guide/island/effect) for reactive behavior that reruns when its dependencies change. Use [`effect.once()`](/guide/island/effect) when something should run once after the island is attached to the DOM.

This separation helps keep component logic easy to scan:

- Events respond to user actions.
- Effects respond to reactive changes; `effect.once()` handles one-time setup.

## SSR and hydration

ilha is designed to work naturally with server rendering and hydration. You can render HTML on the server, send it to the browser, and later activate the island in place.

When using hydratable output, ilha can embed snapshots of state and derived values. It restores them by primitive order, so the component renders immediately without recomputing on first mount.

## Mental model

A useful way to think about an island:

- **Props** are data coming in.
- **State** is reactive data owned by the component.
- **Derived** is data computed from props or state.
- **Render** turns all of that into HTML.
- **Mount** activates behavior in the browser.

Keep this model in mind as you use the API. Each primitive adds one piece to the flow.
