title: Server islands
description: Add SSR to an Ilha SPA with Oxide, render selected islands or whole routes on the server, and keep them interactive through frames.
---

Use [Oxide](https://npmjs.com/package/oxidejs) as the server runtime for an Ilha router app. You keep the SPA authoring model and opt individual islands or whole routes into server rendering.

```ts
// vite.config.ts
import pages from "@ilha/router/vite";
import oxide from "oxidejs/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [
    oxide({ middleware: ["@ilha/router/ssr"] }),
    pages(),
  ],
});
```

This is the recommended SSR setup. You do not need a separate server entry, route renderer, or fetch handler. Oxide loads the route graph and runs the `@ilha/router/ssr` middleware in production.

The middleware serves two internal endpoints:

| Endpoint             | Purpose                                       |
| -------------------- | --------------------------------------------- |
| `POST /__ilha/frame` | Render a server island or server page again.  |
| `GET /__ilha/loader` | Load data during regular-page SPA navigation. |

## Render one island on the server

Put the island in a `*.server.ts` or `*.server.tsx` file. Its render function and server dependencies never ship to the browser:

```tsx
// src/lib/tasks.server.tsx
import { action, derived, each, ilha } from "ilha";

export const TaskList = ilha(() => {
  const items = derived(async function* ({ signal }) {
    yield* getTasks({ signal });
  });

  const remove = action((id: string) => deleteTask(id));

  return (
    <ul>
      {each(items() ?? []).as((task) => (
        <li key={task.id}>
          {task.text}
          <button onclick={() => remove(task.id)}>
            Remove
          </button>
        </li>
      ))}
    </ul>
  );
});
```

Import and render it from a regular page:

```tsx
// src/pages/index.tsx
import { TaskList } from "$lib/tasks.server";
import { ilha } from "ilha";

export default ilha(() => <TaskList />);
```

The router plugin replaces the server module with a small client proxy. The proxy requests the first frame, morphs the returned HTML into place, and reconnects events to server actions.

Streaming `derived()` generators and `action()` calls are matched by primitive order. Keep the same primitive kind at each position on every render so the generated proxy resolves the same transports.

## Render a whole route on the server

Rename a page to `foo.server.tsx` to render the complete route through Oxide. Export a default island and an optional server `load()` function:

```tsx twoslash
// src/pages/user/[id].server.tsx
import type { FrameLoaderContext } from "@ilha/router/server-island-registry";
import { ilha } from "ilha";

export async function load({
  params,
  request,
}: FrameLoaderContext) {
  const response = await fetch(
    new URL(`/api/users/${params.id}`, request.url),
  );
  return response.json() as Promise<{ name: string }>;
}

export default ilha(({ name }: { name: string }) => (
  <main>
    <h1>{name}</h1>
  </main>
));
```

The `load()` result becomes the page props. It runs again at frame time with the current route params, query, request headers, and cancellation signal. A loader `redirect()` navigates the client to its validated target.

Layouts and `+error.ts` boundaries still compose around a server page. During client navigation, the view remains pending until its first frame arrives, so use [`navigating`](/guide/routing/routes-and-navigation#transitions) when you want a route-level loading indicator.

`loader.client()` also works on a server page, but its function executes over RPC and its result does not become server-rendered props. Use it for side effects such as analytics or client document state.

## Read the request during rendering

A server island can read the originating request through `useContext()`:

```tsx twoslash
import { useContext } from "@ilha/router";

const { request } = useContext();
const locale = request?.headers.get("accept-language") ?? "en";
```

Oxide installs the request scope before the router renders. Cookies, authorization, and user-agent headers remain available to loaders and frames. The middleware deliberately does not trust a client-supplied `x-forwarded-for` header.

## How frames keep islands live

```text
Oxide server                         browser
───────────────────────────────────  ───────────────────────────────
POST /__ilha/frame { id, path }      proxy requests a frame
  → match route and run load()         → morph returned HTML
  → restore server island state        → reconnect event sentinels
  → render the next HTML frame          → replay actions over RPC

GET /__ilha/loader?path=…            regular page navigation
  → run the matched loader              → mount or update the view
```

The server owns rendering and state for `*.server.*` islands. The browser owns the DOM proxy and sends action calls back to Oxide.

## Guard production endpoints

Production frame and loader endpoints deny requests by default. Register guards once during server startup:

```ts twoslash
import {
  setFrameAuth,
  setFrameGuard,
  setLoaderGuard,
} from "@ilha/router/server-island-registry";

function isSignedIn(_request: Request) {
  return true;
}
// ---cut---
setFrameGuard((request) =>
  isSignedIn(request)
    ? undefined
    : new Response("Unauthorized", { status: 401 }),
);

setLoaderGuard((request) =>
  isSignedIn(request)
    ? undefined
    : new Response("Unauthorized", { status: 401 }),
);

setFrameAuth({
  trustedOrigins: ["https://app.example.com"],
  csrf: (request) =>
    request.headers.get("x-csrf") === "my-csrf-secret",
});
```

In development, pass `frameGuard` to `pages()` when you need the same session check. Frame request bodies have a 16&nbsp;KiB limit, and invalid paths fail closed.

See [Middleware and security](/guide/routing/middleware-and-security) for the complete guard, origin, CSRF, and header model.

## Use a custom server only when needed

Oxide is the default path. Use the router's manual rendering methods only when another server framework must own the fetch handler.

Every server method accepts a `Request` as its first argument. Prefer that form so route matching, loader context, request-scoped rendering, and redirect validation share one URL:

```ts twoslash
import { router } from "@ilha/router";

const pageRouter = router();
const registry = {};
const request = new Request("https://app.example.com/about");
// ---cut---
const result = await pageRouter.renderResponse(
  request,
  registry,
);
const response = await pageRouter.respond(request, registry);
```

Use the methods according to the result you need:

| Method                                        | Result                                     |
| --------------------------------------------- | ------------------------------------------ |
| `render(url)`                                 | Plain synchronous route HTML.              |
| `renderHydratable(url, registry, options?)`   | HTML with island hydration markers.        |
| `renderResponse(request, registry, options?)` | Structured HTML, head, redirect, or error. |
| `respond(request, registry, options?)`        | Ready-to-send `Response` with headers.     |
| `runLoader(request)`                          | Loader result without rendering a route.   |

Pass `shell` to `respond()` when your host needs a complete document:

```ts twoslash
import { router } from "@ilha/router";

const pageRouter = router();
const registry = {};
const request = new Request("https://app.example.com/about");
const nonce = "abc123";
// ---cut---
const response = await pageRouter.respond(request, registry, {
  cspNonce: nonce,
  shell: (head, html) =>
    `<!doctype html><html${head.htmlAttrs}><head>${head.headTags}</head><body${head.bodyAttrs}>${html}</body></html>`,
});
```

`respond()` handles redirects, 404 responses, serialized head entries, and default security headers. Use `httpResponse()` only when you already have HTML and need a correctly headered response:

```ts twoslash
import { httpResponse } from "@ilha/router";

const response = httpResponse("<h1>Hello</h1>", {
  contentSecurityPolicy: "default-src 'self'",
});
```

## Hydrate manually rendered routes

For a custom host, call `hydrate()` from the browser after the server emits hydratable markup:

```ts twoslash
import { router } from "@ilha/router";

const pageRouter = router();
const registry = {};
// ---cut---
pageRouter.hydrate(registry, {
  root: document.getElementById("root")!,
  target: "#app",
});
```

Oxide file-system routing generates this client wiring for you.
